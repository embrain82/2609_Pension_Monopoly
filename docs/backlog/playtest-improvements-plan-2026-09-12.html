버튼이 비활성화되는 이유도 구별

  • 턴 한도 사용 완료: “이번 턴 추가납입 한도를 모두 사용했습니다. 다음 턴에 다시 납입할 수 있어요.”
  • 생활자금 부족: “납입 가능한 생활자금이 10만원 미만입니다.”
  • 누적 한도 부족: “이번 판에 남은 납입 한도가 10만원 미만입니다.” 상세 설명에서 기존 제도 모형과의 관계를 안내합니다.
  • 턴 잔여 한도가 0원은 아니지만 10만원 미만이면 “이번 턴 남은 한도가 최소 납입금액보다 작습니다”라고 구분합니다. 여러 조건이 겹치면 누적 한도 → 턴 한도 → 생활자금 순으로 주된 이유를 표시합니다. ‘다음 턴 가능’은 누적 한도가 실제 남은 경우에만 안내합니다.

추가납입 화면과 두 번째 행동 시안

사용자에게 필요한 숫자부터

  1. 상단에 이번 턴 납입 사용액 / 200만원과 추가 가능액을 표시합니다.
  2. 빠른 선택은 50만원 · 100만원 · 이번 턴 최대로 제안합니다. 최대 버튼에는 실제 가능액을 함께 표시합니다.
  3. 가능액이 고정 금액보다 작으면 그 고정 버튼을 비활성화합니다. 최대와 고정 선택이 같은 금액이면 버튼을 중복하지 않고 최대 버튼으로 합칩니다.
  4. 미리보기에 실제 납입액, 납입 후 생활자금, 예상 월 연금, 현재 규칙의 공제 효과를 표시합니다. 한도를 넘는 금액과 실제 실행액이 다르게 보이지 않게 합니다.
  5. 실행 버튼을 “100만원 납입”처럼 확정 금액으로 표시합니다. 확정 전 최신 상태로 다시 검사합니다.
  6. 첫 행동이 끝나면 메뉴·빠른 금액·실행 버튼을 같은 계산 결과로 갱신합니다. 추가납입이 막혀도 다른 실행 가능한 운용지시는 계속 선택할 수 있습니다.

시안은 운용지시가 두 번인 턴을 가정합니다. 100만원씩 두 번 또는 최대 200만원을 선택해 제한을 확인할 수 있습니다. 게임 엔진과 연결된 화면은 아닙니다.

한도만큼 납입하도록 강제하지 않습니다. 생활자금을 남기거나 이번 턴 납입을 건너뛰는 선택도 계속 가능합니다. 이번 범위에 자동 납입·새로운 수수료·생활자금 강제 보존 규칙은 추가하지 않습니다.

FB-004 · 포트폴리오 확인은 실제 맨 아래

메뉴에서는 모든 운용 카드와 「이번엔 그대로」 다음에 놓습니다. 추가납입·매수·매도·바꾸기·리밸런싱·디폴트옵션 화면에서는 입력, 실행 버튼, 안내·주문 기록, 피드백 다음에 놓습니다.

  • 모든 운용 화면이 같은 하단 영역을 사용해 포트폴리오 버튼을 한 개만 표시합니다.
  • 디폴트옵션 화면 안에 있는 기존 버튼도 공통 하단으로 옮깁니다. 주문 기록·가정 설명보다 아래가 됩니다.
  • 버튼은 전체 폭의 보조 버튼으로 배치합니다. 문서 흐름상 맨 아래에 두며, 화면 위를 덮는 고정 버튼으로 만들지 않습니다.
  • 포트폴리오에서 「운용 선택으로 돌아가기」를 누르면 원래 하위 화면과 금액·상품 선택을 복원합니다. 포트폴리오 내 닫기로 돌아오는 기존 경로도 확인합니다.
  • 현재의 X 닫기 방식과 운용 카드 디자인·순서를 유지합니다. 별도 ‘취소하고 보드로’ 버튼은 추가하지 않습니다.

FB-005 · 펼침 자체가 눈에 들어오게

현재 시장 안내 아래의 상세 영역을 옅은 녹색 카드로 만들고, 오른쪽에 「상세 보기 ⌄」를 넣습니다. 펼친 뒤에는 「접기 ⌃」로 바뀌고 내용과의 구분선을 표시합니다.

  • 카드의 제목 줄 전체를 누를 수 있도록 하고 터치 높이는 최소 56px로 합니다.
  • 색상 외에 문구와 화살표를 함께 사용합니다. 키보드 포커스는 별도의 주황색 외곽선으로 보여 줍니다.
  • 기본은 접힘입니다. 한 번 열면 같은 턴의 금액 변경·화면 갱신·포트폴리오 왕복 후에도 유지합니다.
  • 새 턴·새 판에서는 접힘으로 시작합니다. 새로고침까지 기억시키는 별도 사용자 설정은 이번 범위에 추가하지 않습니다.
  • 기존에 시장 상세가 있는 운용 화면에 적용합니다. 디폴트옵션 상세 화면 상단에 시장 영역을 새로 중복 삽입하지 않습니다.

실제 구현은 CSS만으로 끝나지 않습니다. 현재 DOM 갱신 함수가 템플릿에 없는 open 속성을 제거합니다. 이 메뉴의 펼침 상태를 UI 상태로 보관하고 렌더에 다시 반영해야 입력을 바꿀 때 갑자기 접히지 않습니다.

구현 방법과 영향을 받는 코드

1. 납입 계산을 한 곳으로 모읍니다

src/engine/contribution-engine.ts에 게임 한도·남은 금액·실행액을 계산하는 순수 함수를 둡니다. 일반 납입과 사건 납입은 이 계산을 공유하되, 제공할 재원만 다르게 전달합니다. 화면의 판단과 엔진 실행 모두 같은 견적을 사용합니다.

// 제안 인터페이스 · 구현 전 설계
contributionBudget(state)
  → { perTurnLimit, usedThisTurn, turnRemaining, annualRemaining }

previewContribution(state, { requested, availableSource })
  → { requested, accepted, remainingAfter, limitedBy, availability }

일반 납입: availableSource = state.cash
보너스 납입: availableSource = event의 납입 대상 금액
usedThisTurn = cashFlows 중 현재 턴 · kind=contribution의 양수 금액 합계

UI / 빠른 금액 / 메뉴 활성화 / 실제 실행 / 사건 선택지
                 ↓ 같은 계산 함수
  • 공통 함수는 game-engine을 import하지 않아 순환 의존성을 피합니다. 기존 acceptedContribution·contributionConstraint는 위 결과를 사용하거나 호환 래퍼로 유지합니다.
  • BlockCode에 턴 한도 제한 사유를 추가하고 actionAvailability까지 연결합니다. 보너스에는 별도 ‘행동 타이밍’ 판정을 잘못 적용하지 않습니다.
  • 요청액이 가능한 금액보다 크면 기존처럼 가능액으로 제한하되, 미리보기와 실행 버튼부터 실제 제한된 금액을 표시합니다. 실행 직전 상태가 바뀌어 견적이 달라졌다면 갱신된 금액을 보여 주고 재확정하게 하며 행동은 차감하지 않습니다.
  • 원금 재원·공제액·환급 대기·외부 납입 흐름에는 실제 수락액만 반영합니다. 동일 실행이 중복 호출되어도 이미 사용한 턴 한도를 기준으로 다시 제한합니다.
  • 보너스의 제목뿐 아니라 “생활자금은 늘지 않습니다” 같은 설명도 실제 남는 금액과 일치시킵니다. 사건에서 제한으로 납입하지 못한 금액은 소실되지 않아야 합니다. 예를 들어 보너스 500만원이면 ‘전액’과 ‘절반’ 모두 제한 후 200만원이 될 수 있으므로, 같은 결과인 선택지를 「200만원 납입 · 300만원 생활자금」 하나로 합칩니다.

2. 기존 저장은 끝까지, 새 게임부터 200만원

진행 중인 판에 새 한도를 소급하면 이미 한 턴에 많이 납입한 기록과 충돌합니다. 진행 중 저장은 기존 규칙으로 마치고, 새 판부터 적용하는 방식을 권장합니다.

// GameState에 선택 필드로 추가하는 제안
contributionPacing?: {
  version: 'v1';
  perTurnLimit: 2000000;
}

필드가 없는 저장 → 이전 규칙, 새 턴 한도 없음
필드가 있는 저장 → 판 생성 시 저장한 한도를 계속 사용
  • balance-config.json에는 새 게임 기본값을 추가하되 policy-rules.json과 기본 금액 버튼값을 한도 자체로 사용하지 않습니다.
  • GameOptions의 명시적 옵션과 실제 새 판 생성 경로에 적용합니다. 옵션을 생략한 기존 테스트·구버전 검증 경로는 기존 동작을 유지합니다.
  • 현재 E 규칙과 c3는 디폴트옵션 장부도 판별합니다. 이를 일괄 다른 버전으로 바꾸지 않고 추가납입 규칙의 별도 버전을 두어 기존 직접매매 기능의 판정을 보존합니다.
  • 저장 파서는 새 선택 필드의 형식·버전·허용 금액, 납입 흐름의 턴·금액·종류와 턴 합계를 검증합니다. 최상위 게임과 복기용 챕터 분기 모두 검사합니다. 필드가 없는 정상 저장은 계속 읽힙니다.
  • 새 판의 한도 사용액은 이미 있는 납입 장부로 복원합니다. 별도 카운터를 새로 만들어 저장값과 어긋나게 하지 않습니다. 새로고침·X 닫기·포트폴리오 열람으로 한도가 초기화되면 안 됩니다.
  • 챕터 다시하기는 분기에 담긴 당시 규칙을 유지합니다. 「같은 시드로 다시」는 새 판이므로 현재 규칙을 적용하고, 결과 공유·기록 내보내기에 추가납입 규칙명/한도를 포함해 이전 판과 구분합니다.
  • 주간 시드도 규칙이 다른 과거 결과와 조건이 같다고 표시하지 않습니다. 기존 최고 점수·업적은 보존하고, 공유할 판의 규칙을 명시합니다.

이전 저장에서 납입 화면을 열면 「이전 규칙으로 진행 중」을 표시하고, 적용되지 않는 200만원 한도 안내는 보여 주지 않습니다. 일반 하위 입력의 새로고침 복원 범위를 확장하는 작업은 포함하지 않으며, 기존 포트폴리오 왕복 보존과 디폴트옵션 초안 복원은 회귀 검증합니다.

3. 운용 모달의 공통 하단과 펼침 상태

renderModal의 운용 창 구성을 기존 시장 안내 → 행동 본문 → 피드백 → 포트폴리오 하단으로 정리합니다. 디폴트옵션은 현재처럼 시장 안내를 생략하고 같은 하단을 사용합니다.

  • renderDefaultTrade 내부 포트폴리오 버튼을 제거하고 data-action="action-portfolio"를 가진 버튼은 공통 하단에서만 생성합니다. 포트폴리오 외의 다른 모달에는 하단을 삽입하지 않습니다.
  • 시장 상세는 native details/summary를 유지합니다. summary 안에 버튼을 중첩하지 않고, 상태 문구는 텍스트로 표현합니다.
  • 해당 메뉴의 toggle 이벤트를 캡처해 UI 상태를 기록하고, 다음 렌더의 open 속성에 반영합니다. 프로그램에 의한 갱신이 다시 불필요한 렌더를 일으키지 않게 동일 값은 무시합니다.
  • 턴/판 전환 시에만 명시적으로 상태를 초기화하고, 포트폴리오 왕복 시 원래 상세 메뉴와 입력 요소의 포커스·스크롤 복귀를 확인합니다. 이 메뉴를 위해 전체 DOM 갱신기의 속성 동기화 규칙을 바꾸지는 않습니다.
